# ポーカーキャッシュゲーム ランキングツール 要件定義書

## 1. 概要

### 1.1 背景
ポーカーのキャッシュゲーム参加者が、各自スマートフォンからプレイ結果を入力し、収支状況を可視化できる仕組みが必要である。

### 1.2 目的
- 参加者ごとの収支を正確に記録する。
- 月次・総合のランキングを自動集計し、競技性と継続利用を高める。
- 個人別の推移を可視化し、振り返りを容易にする。

### 1.3 対象範囲
- Webブラウザ（スマホ中心、PC対応）で利用できるアプリケーション。
- 入力系機能（参加記録登録・セッション終了登録）はプレイヤー名選択後の4桁パスワード認証を行う。
- 閲覧系機能（ランキング・プレイヤー詳細）は認証なしで利用できる。

## 2. 機能一覧（ユースケース形式）

### UC-01 プレイヤー登録
- **目的**: 参加者をシステムに登録する。
- **アクター**: 任意の利用者
- **事前条件**: なし
- **トリガー**: 「プレイヤー登録」操作
- **基本フロー**:
  1. 利用者がプレイヤー名を入力する。
  2. 利用者が4桁の数字パスワードを入力する。
  3. システムが重複チェックとパスワード形式チェック（4桁数字）を行う。
  4. 問題なければパスワードをハッシュ化してプレイヤー情報を登録する。
- **代替/例外フロー**:
  - 既存名と重複する場合はエラー表示し、再入力を促す。
  - パスワードが4桁数字以外の場合はエラー表示し、再入力を促す。
- **事後条件**: プレイヤー一覧に新規プレイヤーが追加される。

### UC-02 キャッシュゲーム参加記録（開始〜リエントリー）
- **目的**: セッション中のバイイン情報を記録する。
- **アクター**: プレイヤー
- **事前条件**: プレイヤーが登録済み
- **トリガー**: 「参加記録登録」操作
- **基本フロー**:
  1. プレイヤー名を選択する。
  2. 4桁パスワードを入力する。
  3. システムが認証を行う。
  4. 日付を入力する。
  5. 初回バイイン額を入力して記録する。
  6. リエントリー時は追加バイイン額を同セッションへ追加入力する。
  7. システムが総バイイン額を更新する。
- **代替/例外フロー**:
  - パスワード不一致の場合はエラー表示し、再入力を促す。
  - 金額が0以下、または数値以外の場合はエラー表示。
- **事後条件**: セッションにバイイン履歴と総バイイン額が保存される。

### UC-03 セッション終了登録（純利益計算）
- **目的**: セッション終了時の最終結果を記録し、純利益を確定する。
- **アクター**: プレイヤー
- **事前条件**: 対象セッションが存在し、少なくとも1件のバイインがある
- **トリガー**: 「セッション終了」操作
- **基本フロー**:
  1. プレイヤー名を選択する。
  2. 4桁パスワードを入力する。
  3. システムが認証を行う。
  4. その日獲得した合計金額を入力する。
  5. システムが純利益 = 合計獲得金額 - 総バイイン額 を自動計算する。
  6. セッション結果を確定保存する。
- **代替/例外フロー**:
  - パスワード不一致の場合はエラー表示し、再入力を促す。
  - 合計獲得金額が未入力/不正値の場合はエラー表示。
- **事後条件**: セッションの純利益が確定し、ランキング集計対象になる。

### UC-04 月次ランキング閲覧
- **目的**: 指定月の純利益順位を確認する。
- **アクター**: 任意の利用者
- **事前条件**: セッション結果が1件以上存在
- **トリガー**: 「月次ランキング」画面表示
- **基本フロー**:
  1. 利用者が対象年月を選択する。
  2. システムが対象月内セッションを集計する。
  3. プレイヤー別純利益合計の降順でランキング表示する。
- **事後条件**: 月次順位が表示される。

### UC-05 総合ランキング閲覧
- **目的**: 全期間累計の純利益順位を確認する。
- **アクター**: 任意の利用者
- **事前条件**: セッション結果が1件以上存在
- **トリガー**: 「総合ランキング」画面表示
- **基本フロー**:
  1. システムが全期間データを集計する。
  2. プレイヤー別累計純利益の降順でランキング表示する。
- **事後条件**: 総合順位が表示される。

### UC-06 プレイヤー詳細閲覧
- **目的**: 個人の成績指標と推移を確認する。
- **アクター**: 任意の利用者
- **事前条件**: 対象プレイヤーのデータが存在
- **トリガー**: プレイヤー名選択
- **基本フロー**:
  1. システムが対象プレイヤーの参加回数、純利益合計を取得する。
  2. 平均稼働金額（純利益 / 参加回数）を計算して表示する。
  3. 時系列ごとの金額推移（例: セッション単位累積損益）をグラフ表示する。
- **事後条件**: 個人分析情報が表示される。

## 3. データモデル（エンティティと属性）

### 3.1 Player（プレイヤー）
- `id` (UUID / PK)
- `name` (string, 必須, 一意)
- `password_hash` (string, 必須, 4桁数字パスワードのハッシュ値)
- `created_at` (datetime)
- `updated_at` (datetime)

### 3.2 Session（セッション）
- `id` (UUID / PK)
- `player_id` (UUID / FK -> Player.id)
- `session_date` (date, 必須)
- `total_buyin_amount` (integer, 必須, 単位: pt, デフォルト0)
- `total_cashout_amount` (integer, 任意: 終了時に入力, 単位: pt)
- `net_profit` (integer, 任意: 終了時に計算確定, 単位: pt)
- `status` (enum: `in_progress` / `closed`)
- `created_at` (datetime)
- `updated_at` (datetime)

### 3.3 BuyIn（バイイン履歴）
- `id` (UUID / PK)
- `session_id` (UUID / FK -> Session.id)
- `entry_type` (enum: `initial` / `reentry`)
- `amount` (integer, 必須, > 0, 単位: pt)
- `recorded_at` (datetime)

### 3.4 MonthlyRankingSnapshot（任意・将来拡張）
- `id` (UUID / PK)
- `year_month` (string, 例: `2026-04`)
- `player_id` (UUID / FK -> Player.id)
- `net_profit_sum` (integer, 単位: pt)
- `rank` (int)
- `calculated_at` (datetime)

> 注: 初期リリースではランキングは都度集計で実装し、性能要件次第でスナップショットを導入する。

## 4. 画面一覧

### 4.1 画面一覧サマリ
1. プレイヤー登録画面
2. 参加記録入力画面（バイイン/リエントリー）
3. セッション終了入力画面（合計獲得金額入力）
4. 月次ランキング画面
5. 総合ランキング画面
6. プレイヤー詳細画面

### 4.2 画面別要件

#### 1) プレイヤー登録画面
- 入力: プレイヤー名、4桁数字パスワード
- 操作: 登録
- 表示: 登録済みプレイヤー一覧、重複エラー、パスワード形式エラー

#### 2) 参加記録入力画面
- 入力: プレイヤー名選択、4桁パスワード、日付、バイイン額
- 操作: 初回バイイン登録、リエントリー追加
- 表示: 現在の総バイイン額、当日セッション状態、認証エラー

#### 3) セッション終了入力画面
- 入力: プレイヤー名選択、4桁パスワード、その日獲得した合計金額
- 表示: 総バイイン額、純利益（自動計算）、認証エラー
- 操作: 結果確定

#### 4) 月次ランキング画面
- 入力: 対象年月
- 表示: 順位、プレイヤー名、月次純利益、参加回数（任意）

#### 5) 総合ランキング画面
- 表示: 順位、プレイヤー名、累計純利益、総参加回数（任意）

#### 6) プレイヤー詳細画面
- 表示:
  - 基本情報（プレイヤー名）
  - 指標（参加回数、純利益合計、平均稼働金額）
  - 時系列グラフ（金額推移）
  - セッション履歴一覧（日付、総バイイン、合計獲得、純利益）

## 5. 非機能要件

### 5.1 UI/UX
- スマートフォンでの入力を主目的としたレスポンシブデザイン。
- 少ないタップ数で記録完了できる導線。

### 5.2 認証
- プレイヤーごとに4桁の数字パスワードを設定する。
- プレイヤー登録時（UC-01）にプレイヤー名と4桁パスワードを同時設定する。
- 参加記録登録・セッション終了登録（UC-02, UC-03）は、プレイヤー名選択後に4桁パスワード入力を必須とする。
- ランキング閲覧・プレイヤー詳細閲覧（UC-04〜06）は認証不要（誰でも閲覧可）。
- パスワードはハッシュ化して保存し、平文では保存しない。
- 誤入力防止のため、名前自由入力ではなく選択式を基本とする。

### 5.3 同時アクセス
- 複数ユーザー同時アクセスを許容。
- 同一セッション更新時の整合性を担保（楽観ロックまたは最終更新優先ルールを設計で定義）。

### 5.4 性能・可用性（初期目標）
- 主要画面表示: 2秒以内を目標。
- 一時的な通信断時は再送可能なエラーハンドリング。

### 5.5 データ品質
- 金額の単位は `pt`（ポイント）とする。
- 金額は整数のみ扱い、小数点は扱わない。
- UI上の金額表示は `pt` を明記する。
- 負数バイインや不正フォーマットを入力時にバリデーション。

## 6. 技術スタック候補（3案）

### 採用方針（確定）
- Geminiレビュー結果に基づき、案Aを採用確定とする。
- 採用構成: Next.js (App Router) + Supabase (PostgreSQL) + Tailwind CSS + shadcn/ui + Recharts + Vercel

### 案A: TypeScriptフルスタック（Next.js + Supabase）
- フロント/サーバー: Next.js (App Router, TypeScript)
- DB: PostgreSQL (Supabase)
- 認証: アプリ内の4桁パスワード認証（`password_hash` 管理）
- グラフ: Recharts or Chart.js
- ホスティング: Vercel
- **メリット**: 実装速度が高い、運用が軽い、スマホ向けUIを作りやすい。
- **留意点**: BaaS依存度が上がる。

### 案B: SPA + API分離（React + FastAPI）
- フロント: React + Vite + TypeScript
- API: Python FastAPI
- DB: PostgreSQL
- グラフ: ECharts or Recharts
- ホスティング: Frontend (Cloudflare Pages等) / API (Render等)
- **メリット**: 役割分離が明確、API再利用性が高い。
- **留意点**: デプロイ構成が2系統になり運用がやや増える。

### 案C: Firebase中心（Flutter Web or React + Firebase）
- フロント: React or Flutter Web
- DB: Firestore
- Functions: Firebase Functions
- ホスティング: Firebase Hosting
- グラフ: 各UI基盤の対応ライブラリ
- **メリット**: 同時アクセス・リアルタイム反映に強い。
- **留意点**: 集計クエリ設計に工夫が必要、ベンダーロックインが強い。
